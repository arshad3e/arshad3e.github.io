1 What the CPU actually runs

A CPU does not understand C. It runs machine instructions, which are numbers stored in memory. Each one does something tiny: copy a value, add two values, compare two values, jump somewhere else.

Those instructions work on registers, a small set of very fast storage slots inside the CPU. A Cortex-M4 has 16 of them, named r0 to r15. Three have special jobs: r13 is the stack pointer (sp), r14 holds the return address (lr), and r15 is the program counter (pc), which points at the next instruction.

Assembly language is the human-readable spelling of those numbers. C is a higher-level language, and the compiler toolchain translates it down. Today you learn exactly how, because almost every hard firmware bug lives in the gap between what your C says and what the machine does.

Stage 1: the preprocessor pastes text

It knows nothing about C. It handles lines that start with #: #include pastes a whole file in, #define swaps text, and #if keeps or drops lines. Comments are removed too.

Your 8-line file became 573 lines because all of stdio.h was pasted in. Open main.i and scroll to the bottom. Your code is there, and in calc.c the word SCALE would already be 10.

Because this is only text substitution, macros have a famous trap:

Always put parentheses around each argument and around the whole macro body. The #ifndef CALC_H lines in the header are an include guard: if the file gets pasted twice, the second copy is skipped.

Stage 2: the compiler turns C into assembly

It checks types and translates one .i file at a time. That one file is called a translation unit. The compiler cannot see any other file, so main.c only needs a promise that scaled_add exists. The line int scaled_add(int a, int b); in the header is that promise.

  • A declaration says a thing exists and what its type is. You can repeat it many times.
  • A definition creates the thing: the function body or the variable's storage. Exactly one is allowed in the whole program.

Stage 3: the assembler produces an object file

It turns assembly into real machine code inside a .o file. Some addresses are still unknown: main calls scaled_add, but nothing yet says where that function will live. The assembler leaves a note called a relocation for the linker to fill in. You can see the unresolved names with nm.

T means defined here, in the text (code) section. U means used here but undefined here. A lowercase t means defined here but private to this file, which is what the static keyword does to a function. The leading underscore is a macOS naming detail. Linux and embedded ELF files do not have it.

Stage 4: the linker connects everything

It matches every U to a T, fills in the relocations, assigns final addresses and writes the executable. Try linking with a piece missing.

On a microcontroller the linker has one more job. A linker script tells it that code goes in flash (address 0x08000000 on your STM32) and variables go in RAM (0x20000000). You will write one on Day 30.

4 Two's complement: how negative numbers work

A byte is 8 bits, and each bit has a place value. As an unsigned number, the places are 128, 64, 32, 16, 8, 4, 2, 1. As a signed number, one thing changes: the top place is worth −128 instead of +128.

Click the bits below. The default pattern, 0xFA, is 250 as unsigned and −6 as signed. These are the same bits read two different ways.

Hex
0xFA
As uint8_t
250
As int8_t
-6
~x + 1 (negated)
0x06

To negate any number: flip every bit, then add 1. In C that is -x == ~x + 1.

CPUs use this system because the same adder circuit works for signed and unsigned. Adding 250 and 6 overflows 8 bits and leaves 0. Adding −6 and 6 also gives 0, using the same bits and the same hardware.

  • Range for N bits: −2N−1 to 2N−1−1. For 8 bits that is −128 to 127.
  • The asymmetry: there is no +128 in 8 bits. For the same reason -INT_MIN and abs(INT_MIN) overflow, which is undefined behavior.
  • Widening: a signed value copies its top bit upward (sign extension). An unsigned value fills with zeros (zero extension). So the source type decides the result:
  • Shift vs divide: dividing truncates toward zero, while right-shifting a negative number rounds down on your compilers. So -7 / 2 is −3, -7 % 2 is −1, but -7 >> 1 is −4. Do not replace a division by 2 with a shift on signed values.

5 Integer promotion: the rule behind most C traps

C applies two rules before it does any arithmetic. Learn them word for word.

Rule 1, promotion. Anything smaller than int (char, short, uint8_t, uint16_t) is converted to int before arithmetic, on any platform where int can hold all its values.
Rule 2, the common type. If the two sides then differ, they convert to one type. The wider type wins. At equal width, unsigned wins, so a negative signed value becomes a huge positive number.

7 Reading assembly: -O0 against -O2

You only need four facts to read simple Arm code. Under the Arm calling convention:

  • Function arguments arrive in r0, r1, r2, r3.
  • The return value goes in r0.
  • bx lr means return to the caller.
  • ldr loads from memory into a register, and str stores a register to memory. [sp, #4] means the memory at the stack pointer plus 4.

-O0 keeps every variable in memory, so a debugger can show it. -O2 keeps values in registers or removes them, which is why a debugger says "optimized out". It is also why memory-mapped hardware registers need volatile, which you will cover on Day 6.

Problem 1 of 3 · Easy · LeetCode 191

Number of 1 Bits

Write a function that takes a 32-bit number and returns how many of its bits are 1.

InputIn binaryOutput
1110113
1281000 00001
0xFFFFFFFDall ones except bit 131

Write: int popcount(uint32_t n);

Hint

n & 1 gives you the lowest bit. n >> 1 moves the next bit into its place.

Solution and explanation

Way 1: check every bit

Takes up to 32 steps, one per bit position. Always say this version first in an interview because it is obviously correct.

The trap: the input must be unsigned. Use int n = -1 and the right shift copies the sign bit back in, so n stays −1 and the loop never ends. I ran this with a guard, and after 40 iterations n was still −1. LeetCode's C version may hand you int n, so cast to uint32_t first.

Way 2: Kernighan's trick, the answer they want

Subtracting 1 turns the lowest 1 bit into 0 and every 0 below it into 1. ANDing with the original then removes just that one bit. The loop runs once per set bit, so a number with three bits set takes three steps.

Way 1 always shifts until the top set bit is gone. Way 2 does only as many steps as there are 1 bits. Both use no extra memory.

Way 3: count in parallel, constant time with no loop

This follow-up separates senior candidates. It treats one register as many small counters, adding neighbors in groups of 2, then 4, then 8 bits.

Each step's groups hold the counts so far. The last line works because multiplying by 0x01010101 adds all four bytes into the top byte: 4 + 4 + 2 + 3 = 13 = 0x0D.

What the interviewer asks next

  • "You call this millions of times. How do you speed it up?" Use a hardware instruction through __builtin_popcount if the chip has one. x86 has POPCNT, and Arm A-class has it through NEON. Cortex-M4 has no population count instruction, so choose between the parallel method and a table.
  • "What about a lookup table?" A 256-entry table is fast but costs 256 bytes of flash, and four lookups per word. A 16-entry nibble table costs 16 bytes and needs eight lookups. On a small MCU, that tradeoff is exactly what they want you to discuss.
Problem 2 of 3 · Easy · LeetCode 231

Power of Two

Given an integer n, return true if it is a power of two: 1, 2, 4, 8 and so on. Do it without a loop.

InputOutputWhy
1true20
16true24
3falsetwo bits set
0falseno bits set
−16falsenegative

Write: bool is_power_of_two(int n);

Hint

Write 1, 2, 4 and 8 in binary. How many bits does each have set? Now connect that to the trick from Problem 1.

Solution and explanation

A power of two has exactly one bit set. n & (n - 1) clears the lowest set bit. If nothing remains, there was only one bit.

It runs in constant time with no extra memory.

Why n > 0 has to be there

  • n = 0: 0 & -1 is 0, so without this check you would wrongly return true.
  • n = INT_MIN: it has one bit set, and n - 1 would overflow, which is UB. && is guaranteed to evaluate left to right and to stop early, so n > 0 fails first and n - 1 never runs. Say that out loud in the interview.

Where this shows up in firmware

  • Ring buffers: a power-of-two size lets you wrap with i & (size - 1) instead of a slow modulo (Day 10).
  • Alignment: (addr & (align - 1)) == 0 tests if an address is aligned, when align is a power of two.

What the interviewer asks next: round up to the next power of two

The shifts copy the highest set bit into every lower position, giving all ones. Adding 1 then carries to the next power of two. The first v-- keeps exact powers unchanged.

Problem 3 of 3 · Easy · LeetCode 136

Single Number

Every number in an array appears exactly twice, except one which appears once. Find that one. Use O(n) time and no extra memory.

InputOutput
[2, 2, 1]1
[4, 1, 2, 1, 2]4
[1]1

Write: int single_number(const int *nums, int len);

Hint

What is x ^ x? What is x ^ 0? Does the order of XOR operations matter?

Solution and explanation

Three properties of XOR make this work:

  • x ^ x = 0, because a number cancels itself.
  • x ^ 0 = x, because zero changes nothing.
  • Order does not matter, so all pairs cancel wherever they appear.

Each bit position works independently: a bit in the result is 1 only if an odd number of inputs had that bit set. One pass, O(n) time, O(1) memory, and it handles negative numbers. A hash set also works, but it uses O(n) memory, which is the reason the question forbids it.

What the interviewer asks next

  • "What if every other number appears three times?" XOR no longer cancels, so you count bits per position, modulo 3. You will solve this on Day 3.
  • "What if two numbers appear once?" Also on Day 3. XOR all of them, then use any set bit of the result to split the array into two groups.
  • "Where is XOR used in real systems?" Parity checks, RAID recovery of a lost disk, and many checksums.
  • "Is XOR swap a good idea?" No. a ^= b; b ^= a; a ^= b; sets the value to 0 when both names refer to the same address. It is also harder to read, and a compiler can already swap efficiently with a temporary.

Step 5 · 20 minutes

Answer these out loud

Say your answer first, as if an interviewer just asked it. Then open the model answer and compare. Keep each answer under a minute. Record yourself on at least two of them.

Walk me through what happens when you run gcc on a C file.

"Four stages. The preprocessor handles includes and macros and produces pure C text. The compiler translates that one translation unit into assembly, and that is where type checking and optimization happen. The assembler turns it into an object file containing machine code, a symbol table and relocations for addresses it doesn't know yet. The linker combines all the object files, resolves each undefined symbol to one definition and assigns final addresses. On an embedded target, a linker script decides what goes in flash and what goes in RAM."

What is the difference between a compile error and a link error?

"A compile error is a problem within one file, such as a type error or an undeclared name. A link error is a problem between files. The compiler accepted the code because a declaration promised the symbol exists, but the linker can't find a definition, or finds two. Undefined symbol usually means a missing source file or library. Duplicate symbol often means a variable was defined in a header rather than declared extern."

What does (unsigned)-1 > 0 evaluate to, and why?

"True. Converting −1 to unsigned is well defined: the value is taken modulo 232, giving 4294967295, which has all bits set. That is greater than zero. The related trap is -1 < 1u, which is false, because the usual arithmetic conversions turn the −1 into unsigned before comparing."

Signed overflow is undefined. What can the optimizer do with that?

"It can assume overflow never happens and optimize on that basis. For example, x + 1 > x compiles to a constant 1. I've confirmed that: with INT_MAX it returned 0 at -O0 and 1 at -O2. It also lets the compiler reason about loop bounds. The practical risk is that an overflow check written as a + b < a can be deleted. You check before adding, or use __builtin_add_overflow, and test with UBSan."

Give the sizes of int, long and a pointer on ILP32 and LP64.

"ILP32, which is Cortex-M and 32-bit Arm: int 4, long 4, pointer 4. LP64, which is 64-bit Linux and macOS: int 4, long 8, pointer 8. 64-bit Windows is LLP64, where long stays 4 and pointers are 8. So I use stdint.h types where width matters, and size_t or uintptr_t for sizes and addresses rather than int."

uint8_t a = 200, b = 100. What is a + b?

"300, and its type is int. Both operands are promoted to int first, so nothing overflows, and sizeof(a + b) is 4. If you assign the result back to a uint8_t you get 44, which is 300 modulo 256. Conversion to unsigned is well defined, so this wraps silently without UB."

uint16_t a = 65535, b = 65535. What is wrong with uint32_t c = a * b?

"Both promote to signed int on a 32-bit platform, because int can hold every uint16_t value. The product, about 4.29 billion, doesn't fit in a signed int, so it's signed overflow and undefined behavior, even though every variable you can see is unsigned. The fix is to cast one operand: (uint32_t)a * b."

Explain two's complement. How do you negate a number?

"The top bit has a negative place value, so in 8 bits it's worth −128. To negate, flip all bits and add one. It's used because addition and subtraction use the same circuit for signed and unsigned. The range is asymmetric, −128 to 127, so negating or taking abs of the minimum value overflows."

Undefined, unspecified and implementation-defined: what is the difference?

"Implementation-defined means the compiler chooses and documents it, like the size of int or whether char is signed. Unspecified means several outcomes are allowed with no documentation required, like the evaluation order of function arguments. Undefined means the standard places no requirement at all, like signed overflow or reading out of bounds. The compiler may assume undefined behavior never occurs, so it's the dangerous one."

Is char signed or unsigned?

"It's implementation-defined. On x86 it's normally signed. On Arm, including Cortex-M, it's normally unsigned. I saw c < 0 compile to a constant zero for Cortex-M. So I use char only for text, and int8_t or uint8_t for numbers. Plain char used to hold a return value that can be negative is a classic porting bug."

A bug only appears in the release build, not in debug. How do you approach it?

"I treat it as likely UB, an uninitialized variable, a missing volatile, or a timing problem. First I turn on all warnings and build with ASan and UBSan, plus -O2 -g so I keep the optimization and still get symbols. I reduce the optimization file by file to find which translation unit triggers it. Then I compare the generated assembly around the failure. On a target, I also check stack size, because optimization changes stack use, and any shared variable used by an interrupt. If timing changes the bug, I use a GPIO toggle or a trace buffer rather than printf."

What does static do on a function, and on a global variable?

"At file scope, static gives internal linkage: the name is private to that translation unit. nm shows a lowercase t instead of T. This prevents name collisions, and it lets the compiler inline the function and drop the standalone copy. In a large firmware image, this can also reduce code size. Inside a function, static means something else: the variable keeps its value between calls and has static storage."

Q1
unsigned a = 1;
int b = -2;
printf("%d", a + b > 0);
Answer

1. b converts to unsigned, so a + b is 4294967295, which is greater than 0.

Q2
uint8_t x = 255;
x++;
printf("%u", x);
Answer

0. The value becomes 256 as an int, then is stored back in 8 bits. Well defined.

Q3
int8_t y = 127;
y++;
printf("%d", y);
Answer

−128. The addition happens in int and gives 128, so there is no overflow. Converting 128 back to int8_t is implementation-defined rather than undefined. Clang and gcc wrap it.

Q4
uint8_t n = 0xF0;
printf("%X", n >> 4 | n << 4);
Answer

F0F. You might have expected a nibble swap giving 0F. Promotion to int keeps the upper bits from n << 4, which is 0xF00. To fix it, cast the result: (uint8_t)(n >> 4 | n << 4).

Q5
char c = 0xFF;
printf("%d", c == 0xFF);
Answer

0 on your Mac, 1 on Cortex-M. On the Mac, c is signed and holds −1, compared against 255. On Cortex-M, c is unsigned and holds 255. I checked the Cortex-M result in its generated assembly.

Q6
short s = 1;
printf("%zu %zu", sizeof(s), sizeof(s + s));
Answer

2 4. s + s is promoted to int. Note that sizeof does not evaluate its operand.

Q7
long long z = -1;
unsigned u = 1;
printf("%d", z < u);
Answer

1. long long is wider, so u converts to a signed long long and −1 stays −1. Unsigned wins only at equal width.

Q8
printf("%d %d %d", -7 / 2, -7 % 2, -7 >> 1);
Answer

−3 −1 −4. Division truncates toward zero, the remainder takes the sign of the dividend, and the arithmetic shift rounds down.

Q9
size_t len = strlen("");
printf("%d", len - 1 > 5);
Answer

1. len - 1 wraps around to the largest size_t value. Writing i < strlen(s) - 1 has the same bug with an empty string. Use i + 1 < strlen(s).

Q10
uint32_t w = 0xFFFFFFFF;
uint64_t v = w + 1;
printf("%llu", (unsigned long long)v);
Answer

0. The addition happens in 32 bits and wraps before the result is widened. The type you assign to doesn't change how the right side is calculated. Writing (uint64_t)w + 1 gives 4294967296.
